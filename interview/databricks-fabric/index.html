    Databricks & Microsoft Fabric¶

    26. PySpark in Databricks¶

    Q: How does Databricks optimise Spark workloads?

    30-sec answer

    Databricks runs a proprietary Spark distribution with several key additions: the Photon execution engine for vectorised query processing, Delta Lake as the default table format, Unity Catalog for governance, and automated cluster management. These combine to make Spark workloads faster and easier to operate than open-source Spark.

    Deep dive

    Photon execution engine:

    Photon is a C++-based vectorised execution engine that replaces parts of the standard JVM-based Spark execution for SQL and ETL workloads. Instead of processing one row at a time, it processes batches of rows (vectors) using CPU SIMD instructions.

    Benefits: - 2–10x faster on SQL aggregations, joins, and scans - Better CPU cache utilisation - Native handling of Delta file formats

    # No code changes needed — Photon is transparent
# Just enable it on the cluster config:
# Runtime: Databricks Runtime 9.1+ with Photon enabled

    Delta Live Tables (DLT):

    DLT is Databricks' declarative pipeline framework — you define what tables should contain, and DLT manages execution order, retries, and data quality:

    import dlt

@dlt.table(comment="Raw customer events")
def bronze_events():
    return spark.readStream.format("cloudFiles") \
        .option("cloudFiles.format", "json") \
        .load("/mnt/raw/events")

@dlt.table(comment="Cleaned customer events")
@dlt.expect_or_drop("valid_customer", "customer_id IS NOT NULL")
def silver_events():
    return dlt.read_stream("bronze_events").filter(col("status") == "active")

    Unity Catalog:

    Unity Catalog provides three-level namespace governance (catalog.schema.table), fine-grained access control, data lineage tracking, and cross-workspace sharing. In interviews, mention it as the governance layer that sits above the compute layer.

    Cluster types:

    Type Use case
    All-purpose Interactive notebooks, development
    Job cluster Production pipeline runs — spun up, runs job, terminates
    SQL Warehouse BI queries via Databricks SQL

    Key Databricks-specific patterns: - dbutils.fs for filesystem operations - dbutils.widgets for parameterised notebooks - %run for notebook chaining - display() instead of show() for richer output

    Follow-up: Why is Photon important?

    30-sec answer

    Photon is important because it removes the JVM overhead from the hot path of SQL and ETL execution. Standard Spark uses JVM bytecode generation; Photon uses C++ with vectorised SIMD instructions. For compute-heavy workloads — large aggregations, joins, scans — this translates to 2–10x throughput improvement with no code changes.

    27. PySpark in Microsoft Fabric¶

    Q: How is PySpark used in Microsoft Fabric?

    30-sec answer

    In Fabric, PySpark runs in Data Engineering notebooks against data stored in OneLake lakehouses. Notebooks use a managed Spark runtime — you don't configure clusters, Fabric handles it. Data is stored as Delta tables on OneLake and can be accessed by Spark, SQL endpoints, and Power BI DirectLake simultaneously.

    Deep dive

    The Fabric architecture:

    OneLake (unified storage layer — ADLS Gen2 underneath)
    ├── Lakehouse A
    │     ├── Tables/  ← Delta tables (Spark reads/writes here)
    │     └── Files/   ← Raw files
    ├── Lakehouse B
    └── Warehouse (T-SQL endpoint)

Compute engines all point to same OneLake:
    ├── Spark (PySpark notebooks)
    ├── SQL Analytics Endpoint (auto-generated, read-only via T-SQL)
    └── Power BI DirectLake (reads Delta directly, no import)

    Key Fabric concepts for interviews:

    OneLake shortcuts: Reference data from other lakehouses, Azure storage, or AWS S3 without copying it. Spark reads shortcuts transparently.

    V-Order: Fabric applies V-Order (a proprietary Parquet optimisation) to all Delta tables by default. It improves read performance for Power BI DirectLake and SQL endpoint queries. No code change needed — it's applied at write time.

    Spark in Fabric vs Databricks:

    Feature Databricks Microsoft Fabric
    Execution engine Photon (optional) Standard Spark + V-Order
    Storage Delta on cloud storage OneLake (Delta)
    Governance Unity Catalog Fabric permissions + Purview
    Orchestration Workflows / DLT Data Factory pipelines
    BI integration Partner connect / Tableau Native Power BI DirectLake

    Typical Fabric notebook pattern:

    # Read from lakehouse table (no path needed — just use table name)
df = spark.read.format("delta").table("silver_customers")

# Or via path
df = spark.read.format("delta").load("abfss://workspace@onelake.dfs.fabric.microsoft.com/lakehouse/Tables/silver_customers")

# Write back
df_transformed.write.format("delta").mode("overwrite").saveAsTable("gold_customers")

    Fabric-specific gotchas: - Spark pools are managed — you can't install arbitrary system libraries without using custom environments - Default Spark config may differ from Databricks — test shuffle partition counts - DirectLake has limitations on certain DAX functions — know when it falls back to DirectQuery mode

    Follow-up: How are jobs orchestrated in Fabric?

    30-sec answer

    Fabric uses Data Factory pipelines to orchestrate Spark notebook execution. A pipeline activity calls a notebook, passes parameters, and handles retry logic and dependencies. For more complex orchestration — conditional branching, parallel execution, event-based triggers — you chain multiple activities within the pipeline canvas.
