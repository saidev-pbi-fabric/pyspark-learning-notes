    Query Optimization¶

    6. Catalyst Optimizer¶

    Q: What does the Catalyst optimizer do?

    30-sec answer

    Catalyst is Spark's query optimisation engine. It takes your logical query plan — what you wrote in PySpark — and rewrites it into the most efficient physical execution plan before any data is read. It applies rules like pushing filters closer to the source, eliminating unnecessary columns, and selecting the best join strategy.

    Deep dive

    Catalyst works in four phases:

    1. Analysis       → Resolves column names, table references, data types
2. Logical Opt    → Applies rule-based optimisations (predicate pushdown, projection pruning)
3. Physical Plan  → Generates multiple physical plans, picks the cheapest via cost model
4. Code Gen       → Compiles the plan to JVM bytecode (via Tungsten whole-stage codegen)

    Key optimisations Catalyst applies automatically:

    Optimisation What it does
    Predicate pushdown Moves filter() as close to storage as possible
    Projection pruning Reads only columns you actually use
    Constant folding Evaluates constant expressions at compile time
    Join reordering Puts smaller tables on the broadcast side
    Null propagation Simplifies null comparisons in expressions

    Practical example:

    # You write this
df = spark.read.format("delta").load("/silver/sales")
result = df.select("region", "amount").filter(col("region") == "EMEA").groupBy("region").agg(sum("amount"))

    Catalyst rewrites the execution order to: 1. Read only region and amount columns (projection pruning) 2. Filter rows where region == "EMEA" at scan time (predicate pushdown) 3. Then group and aggregate

    The code you wrote is logically correct but not execution-ordered — Catalyst fixes that for you.

    Follow-up: Examples of Catalyst optimisations?

    30-sec answer

    The three most impactful: predicate pushdown (filters applied at the storage layer before data is read), projection pruning (only requested columns are scanned), and join reordering (smaller datasets are placed on the broadcast side to avoid expensive sort-merge joins).

    7. Adaptive Query Execution (AQE)¶

    Q: What is Adaptive Query Execution?

    30-sec answer

    AQE is a runtime optimisation system introduced in Spark 3.0. Unlike Catalyst, which optimises before execution, AQE monitors what actually happens during a query and adjusts the plan mid-flight — changing join strategies, merging small shuffle partitions, and handling skewed data automatically.

    Deep dive

    Catalyst optimises based on statistics collected before execution. Those statistics can be wrong — especially for data with skew, after joins, or when stats haven't been refreshed. AQE fixes this by making decisions based on real runtime data.

    Three main AQE features:

    1. Dynamic coalescing of shuffle partitions After a shuffle, AQE checks the actual output partition sizes. If many partitions are tiny, it merges them before the next stage — avoiding thousands of small tasks.

    spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

    2. Dynamic switching of join strategies If a table was estimated to be large but turns out small at runtime, AQE switches from a sort-merge join to a broadcast join on the fly.

    3. Dynamic skew join optimisation If one partition is 5x larger than the median, AQE splits that partition and processes it separately — preventing one slow task from blocking the entire stage.

    spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")

    AQE is enabled by default in Spark 3.2+ — but knowing it exists helps you diagnose cases where it's not firing as expected.

    Follow-up: What problems does AQE solve?

    30-sec answer

    AQE specifically targets two common production problems: data skew (where one partition holds far more data than others, slowing the whole job) and inefficient shuffle partitions (where the default 200 partitions creates either too many small tasks or too few large ones). It handles both dynamically at runtime.

    8. Predicate Pushdown¶

    Q: What is predicate pushdown?

    30-sec answer

    Predicate pushdown moves filter conditions as close to the data source as possible — ideally to the storage layer — so Spark reads only the rows it needs. Instead of loading a full table and filtering in memory, the filter is applied during the file scan itself.

    Deep dive

    Without predicate pushdown: 

    Read 500GB table into Spark memory → filter 490GB away → process 10GB

    With predicate pushdown: 

    Storage layer reads only matching rows → Spark receives 10GB → process 10GB

    How it works with Delta / Parquet:

    Delta and Parquet files store column statistics (min, max, null count) at the file level. When Catalyst pushes a predicate like date >= '2025-01-01', it checks those stats and skips entire files that can't contain matching rows — without reading them at all.

    # Predicate pushdown fires here — Delta skips non-matching files at scan time
df = spark.read.format("delta").load("/silver/events") \
    .filter(col("event_date") >= "2025-01-01") \
    .filter(col("region") == "UK")

    When predicate pushdown doesn't fire: - Filters applied after a join or aggregation (no longer at source) - Using UDFs in filter conditions (Catalyst can't translate them to storage predicates) - Complex expressions that can't be serialised to the storage format

    Tip: Run df.explain(True) and look for PushedFilters in the physical plan output to confirm pushdown is happening.

    Follow-up: Why is it important?

    30-sec answer

    It reduces I/O — the most expensive operation in distributed systems. Reading less data from storage means less network transfer, less memory pressure, and faster queries. On large Delta tables the difference between a scan of 1TB vs 10GB can be the difference between a 2-minute query and a 20-minute one.

    9. Projection Pruning¶

    Q: What is projection pruning?

    30-sec answer

    Projection pruning means Spark reads only the columns your query actually needs. If your table has 50 columns but your query uses 3, Spark and the underlying storage layer (Parquet/Delta) will skip the other 47 entirely — at the file level, before data reaches executors.

    Deep dive

    Parquet (the underlying format for Delta) is columnar — each column is stored separately on disk. This means skipping a column is a genuine I/O saving, not just filtering in memory.

    # Spark reads ALL 50 columns — wasteful
df = spark.read.format("delta").load("/silver/customers")
result = df.select("customer_id", "country", "signup_date")

# Catalyst sees only 3 columns are needed and prunes the rest at scan time

    Why SELECT * is dangerous in Spark: It disables projection pruning. Every column gets read, even ones you never use. On wide tables with many columns (audit fields, metadata, nested structs), this adds significant I/O cost.

    Projection pruning + predicate pushdown together:

    These two optimisations combine to make Delta table scans extremely efficient: - Predicate pushdown skips rows (entire files or row groups) - Projection pruning skips columns

    Used together on a 1TB table, you might end up reading only a few GB of relevant data.

    Follow-up: Why is it beneficial?

    30-sec answer

    It reduces both disk I/O and memory usage. In columnar formats like Parquet and Delta, columns not needed are simply not read from disk. On wide tables — 30, 50, 100 columns — this can cut scan time and memory footprint dramatically, especially when queries only need 3–5 columns.
