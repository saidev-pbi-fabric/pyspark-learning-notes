    Pipeline Architecture¶

    28. Incremental Data Engineering Pattern¶

    Q: What is a common incremental processing pattern?

    30-sec answer

    The standard pattern is watermark-based incremental loading: track a high-watermark (the max load_timestamp from the last run), query only new records since that mark, process them, and update the watermark. For streaming sources, Auto Loader or Structured Streaming handles this automatically via checkpoints.

    Deep dive

    Why incremental matters:

    Full-load pipelines reprocess everything every run — as tables grow, so does compute cost. Incremental pipelines process only what changed. A table with 1 billion rows processed daily full-load vs processing only 500K new rows per day is a 2000x difference in compute.

    Pattern 1: Watermark table approach (batch)

    # Read last processed timestamp from control table
last_watermark = spark.read.format("delta").table("pipeline_control") \
    .filter(col("pipeline_name") == "customer_events") \
    .select("last_processed_ts").first()[0]

# Load only new data
df_new = spark.read.format("delta").table("bronze_events") \
    .filter(col("load_timestamp") > last_watermark)

# Process
df_silver = transform(df_new)

# Write to silver
df_silver.write.format("delta").mode("append").saveAsTable("silver_events")

# Update watermark
new_watermark = df_new.agg(max("load_timestamp")).first()[0]
spark.sql(f"""
    UPDATE pipeline_control
    SET last_processed_ts = '{new_watermark}', updated_at = current_timestamp()
    WHERE pipeline_name = 'customer_events'
""")

    Pattern 2: Auto Loader (Databricks / Fabric)

    # Auto Loader tracks which files have been processed in the checkpoint
df = spark.readStream.format("cloudFiles") \
    .option("cloudFiles.format", "parquet") \
    .option("cloudFiles.schemaLocation", "/mnt/schemas/events") \
    .load("/mnt/raw/events/")

df.writeStream \
    .format("delta") \
    .option("checkpointLocation", "/mnt/checkpoints/bronze_events") \
    .trigger(availableNow=True) \   # Batch-style: process all new, then stop
    .start("/mnt/bronze/events")

    Pattern 3: CDC with Delta MERGE

    # Source contains change records with operation type
source = spark.read.format("delta").table("cdc_feed")

DeltaTable.forName(spark, "silver_customers").alias("t").merge(
    source.alias("s"),
    "t.customer_id = s.customer_id"
).whenMatchedDelete(condition="s.op = 'D'") \
 .whenMatchedUpdateAll(condition="s.op = 'U'") \
 .whenNotMatchedInsertAll(condition="s.op = 'I'") \
 .execute()

    Idempotency — important for production:

    Incremental pipelines should be idempotent — running the same load twice should produce the same result. Design for this by: - Using MERGE instead of append where duplicates are possible - Using replaceWhere for partition overwrites - Adding deduplication before writing

    Follow-up: Why is incremental processing important?

    30-sec answer

    Cost and scalability. Full reloads become unmanageable as data grows — a 10TB table that adds 1GB daily costs 10x more to process as a full reload than as an incremental load. Incremental patterns also enable near-real-time data freshness without the infrastructure complexity of full streaming pipelines.

    29. Multi-Workload Table Strategy¶

    Q: Why maintain separate tables for different workloads?

    30-sec answer

    Different consumers have different needs. A Spark ETL job wants large Delta files, minimal metadata, and efficient sequential scans. A Power BI DirectLake report wants V-Order optimised files, small row groups, and columns ordered for dictionary encoding. These requirements conflict — optimising one table for both is a compromise that performs poorly for both.

    Deep dive

    The Medallion architecture addresses this by maintaining different table layers with different optimisation profiles:

    Bronze (raw, append-only)
    ↓ Spark ETL
Silver (cleaned, validated — optimised for Spark processing)
    ↓ Spark aggregation
Gold (aggregated, business-ready — optimised for BI consumption)
    ↓
Power BI DirectLake / SQL Endpoint

    Silver vs Gold optimisation differences:

    Concern Silver (Spark-optimised) Gold (BI-optimised)
    File size 512MB–1GB 100–256MB (smaller for DirectLake)
    Partitioning Date-based for incremental loads Minimal — pre-aggregated
    Z-ordering Join keys, filter columns Dimension columns used in slicers
    Schema Granular — all fields retained Pre-joined, denormalised
    Row count Millions per table Thousands to low millions

    The Gold layer design principle:

    Gold tables should answer specific business questions, not store raw data. If the question is "monthly revenue by region", the Gold table has exactly those columns — pre-aggregated, pre-joined, ready to query without further transformation.

    # Gold table — pre-aggregated, BI-ready
df_gold = df_silver \
    .groupBy("year", "month", "region", "product_category") \
    .agg(
        sum("revenue").alias("total_revenue"),
        countDistinct("customer_id").alias("unique_customers"),
        avg("order_value").alias("avg_order_value")
    )

df_gold.write.format("delta") \
    .mode("overwrite") \
    .option("overwriteSchema", "true") \
    .saveAsTable("gold.monthly_revenue_summary")

    DirectLake considerations (Fabric):

    DirectLake reads Delta files directly without import. For best performance: - Keep Gold table files small (better column group skipping in Power BI) - V-Order is applied automatically in Fabric - Avoid complex nested types — flatten structs before writing to Gold - Pre-calculate measures where possible — reduce DAX complexity

    Follow-up: Example?

    30-sec answer

    Silver tables are optimised for Spark processing — large files, partitioned by date, Z-ordered on join keys. Gold tables are optimised for BI consumption — smaller files, denormalised schema, pre-aggregated to the grain a report needs. A Power BI report reading from Gold runs in seconds; reading from Silver would trigger a full aggregation scan every time.

    30. Production PySpark Pipeline Architecture¶

    Q: What does a production PySpark pipeline look like?

    30-sec answer

    A production pipeline follows the Medallion pattern: raw data lands in Bronze (append-only, minimal transformation), Spark jobs clean and validate it into Silver (structured, typed, deduplicated), and further aggregation produces Gold tables for BI and analytics. Each layer is Delta, each step is orchestrated, monitored, and idempotent.

    Deep dive

    Full production architecture:

    Landing Zone (raw files — ADLS / S3 / OneLake Files)
        ↓  Auto Loader / Structured Streaming
Bronze Layer (Delta — raw, append-only, schema-on-read)
        ↓  PySpark batch job or streaming
Silver Layer (Delta — clean, typed, deduplicated, validated)
        ↓  PySpark aggregation job
Gold Layer (Delta — pre-aggregated, BI-ready, denormalised)
        ↓
    ├── Power BI DirectLake / SQL Endpoint
    ├── ML feature store
    └── Downstream APIs / exports

    What makes a pipeline "production-grade":

    1. Idempotency Every pipeline run produces the same result if run multiple times. Use MERGE, partition overwrites, or deduplication logic.

    2. Data quality gates 

    # Count-based check
row_count = df_silver.count()
assert row_count > 0, "Silver table is empty — pipeline blocked"

# Null check on critical columns
null_count = df_silver.filter(col("customer_id").isNull()).count()
assert null_count == 0, f"{null_count} null customer_ids found"

    3. Schema enforcement Delta rejects schema mismatches by default. Use mergeSchema only when intentional schema evolution is expected.

    4. Lineage and observability - Log row counts at each layer - Track pipeline run metadata (start time, end time, rows processed, errors) - Use Unity Catalog or Purview for cross-table lineage

    5. Orchestration with retry logic 

    # Databricks Workflow / Fabric Pipeline
# Configure: max retries = 3, retry on timeout, alert on failure

    6. Environment separation 

    dev/ sandbox/ (small data, frequent changes)
staging/ (production data volume, integration testing)
prod/ (live pipelines, monitored, alerting enabled)

    The mindset shift from junior to senior:

    Junior thinking:
    Write a script → process data → output a file

Senior thinking:
    Design for failure — what happens when the source is late?
    Design for scale — what happens when volume 10x's?
    Design for operations — how does oncall diagnose a failure at 2am?
    Design for correctness — how do you know the numbers are right?

    Follow-up: Why use this architecture?

    30-sec answer

    The Medallion architecture with Delta tables gives you modularity (each layer has a clear responsibility), reliability (ACID transactions at every layer), observability (row counts, data quality checks at each boundary), and flexibility (Gold tables can be rebuilt from Silver without re-ingesting raw data). It's the architecture that scales from a prototype to a system processing billions of events daily.
