    Performance & Debugging¶

    23. Spark Caching Strategy¶

    Q: When should caching be used?

    30-sec answer

    Cache when you reuse the same DataFrame multiple times in a pipeline and the computation to produce it is expensive. Don't cache raw source tables — Delta already handles file skipping and pushdown efficiently. Don't cache data you'll only use once. Cache intermediate aggregations or filtered datasets that feed multiple downstream steps.

    Deep dive

    Caching stores a DataFrame in executor memory (or memory + disk) so it doesn't need to be recomputed on each action.

    # Without cache — df_filtered is computed twice
df_filtered = df.filter(col("status") == "active").join(df_lookup, "id")
count = df_filtered.count()           # Spark runs the full pipeline
summary = df_filtered.groupBy("region").agg(sum("amount"))  # Runs again

# With cache — computed once, reused
df_filtered.cache()
df_filtered.count()      # First action triggers computation and caches result
summary = df_filtered.groupBy("region").agg(sum("amount"))  # Read from cache

# Always unpersist when done
df_filtered.unpersist()

    Cache storage levels:

    from pyspark import StorageLevel

df.persist(StorageLevel.MEMORY_ONLY)           # Fastest, drops if OOM
df.persist(StorageLevel.MEMORY_AND_DISK)       # Spills to disk if OOM (safer)
df.persist(StorageLevel.DISK_ONLY)             # Slow, use only for very large data
df.cache()                                      # Shortcut for MEMORY_AND_DISK_DESER

    What not to cache:

    Don't cache Why
    Raw Delta tables Delta's data skipping + pushdown is already efficient
    DataFrames used only once Caching has overhead — wastes memory
    Streaming DataFrames Not supported in the same way
    Very large DataFrames Risk of OOM or excessive GC pressure

    Signs you need caching: - The same DataFrame appears in multiple branches of your pipeline - Spark UI shows the same stage running twice with identical plans - Job has iterative computation (loops, graph algorithms)

    Follow-up: What should not be cached?

    30-sec answer

    Raw Delta tables — they already benefit from file skipping, column pruning, and predicate pushdown at the storage layer, so caching them just wastes executor memory. Also avoid caching DataFrames you only read once — the overhead of writing to cache storage isn't worth it for single-use data.

    24. Spark Checkpointing¶

    Q: What is checkpointing?

    30-sec answer

    Checkpointing saves a DataFrame's computed state to durable storage, breaking the lineage chain. Unlike caching (which is memory-based and lost on failure), checkpoints are written to a reliable filesystem and survive executor failures or context resets.

    Deep dive

    Every transformation adds a node to the RDD lineage graph. In long-running or iterative jobs, that lineage can become extremely long:

    read → filter → join → groupBy → window → join → groupBy → join → ...

    If any step fails, Spark recomputes the entire lineage from scratch. Checkpointing truncates that chain:

    # Set checkpoint directory (persistent storage)
spark.sparkContext.setCheckpointDir("/mnt/checkpoints/job_xyz")

# Checkpoint a DataFrame — writes to disk and breaks lineage
df_intermediate.checkpoint()

# Truncated lineage — recovery only goes back to checkpoint, not original source

    Checkpoint vs Cache:

    Cache Checkpoint
    Storage Executor memory/disk Durable filesystem (HDFS, ADLS, S3)
    Lineage Preserved Truncated
    Fault tolerant No (lost on executor failure) Yes
    Use case Reuse within a session Long lineage, iterative jobs, streaming

    Structured Streaming checkpoints:

    In streaming, checkpoints are mandatory — they store the stream's current offset and state:

    df_stream.writeStream \
    .format("delta") \
    .option("checkpointLocation", "/mnt/checkpoints/stream_xyz") \
    .start("/mnt/silver/events")

    Without a checkpoint, a streaming job that restarts loses track of where it was in the source and reprocesses data.

    Follow-up: When is checkpointing used?

    30-sec answer

    Two main scenarios: streaming pipelines (mandatory — stores offset and state so restarts resume where they left off) and iterative batch computations like graph algorithms or ML training loops where lineage grows very long. In iterative jobs, checkpointing every few iterations prevents Spark from needing to replay the full history on failure.

    25. Spark Debugging¶

    Q: How do you debug slow Spark jobs?

    30-sec answer

    Start with the Spark UI — look at the Stages tab for tasks that are taking disproportionately long, the SQL tab for the physical execution plan, and the Executors tab for GC pressure or memory issues. Most slow jobs fall into three categories: data skew, large shuffles, or insufficient partitioning.

    Deep dive

    Step-by-step debug approach:

    1. Check the Spark UI — Stages tab - Are all tasks in a stage completing at similar times, or is one task running 10x longer? → Data skew - Are there many stages? → Too many shuffles - Is shuffle read/write size very large? → Reduce data volume before shuffle

    2. Check the SQL tab — physical plan 

    df.explain(True)  # Shows logical + physical plan
df.explain("formatted")  # Cleaner output in Spark 3.x
    Look for: - Exchange nodes → shuffle operations - BroadcastExchange → broadcast join (good for small tables) - SortMergeJoin → expensive, check if broadcast is possible - Filter pushed below Scan → predicate pushdown working

    3. Check the Executors tab - High GC time (>10% of task time) → memory pressure, tune executor memory or reduce data - Some executors doing much more work than others → skew

    Common root causes and fixes:

    Symptom Root cause Fix
    One task takes 100x longer Data skew Salting, AQE skew join
    Many small stages Too many shuffles Reduce groupBy/join operations, pre-partition
    OOM errors Executor memory too small or cache overuse Tune spark.executor.memory, reduce cache
    Long GC pauses Too many objects in JVM heap Use Tungsten off-heap, increase memory
    Job takes forever but tasks are fast Driver bottleneck from .collect() Avoid collecting large datasets to driver

    Quick diagnostic code:

    # Check partition sizes
df.rdd.mapPartitionsWithIndex(lambda i, it: [(i, sum(1 for _ in it))]).collect()

# Check data distribution on a key
df.groupBy("customer_id").count().orderBy(col("count").desc()).show(20)

# Time a specific operation
import time
start = time.time()
df.count()
print(f"Elapsed: {time.time() - start:.2f}s")

    Follow-up: Most common cause of slow jobs?

    30-sec answer

    Data skew and large shuffle operations — they account for the majority of slow job complaints in production. Data skew means one task does the work of a hundred others, making the whole stage wait. Large shuffles mean massive disk I/O and network transfer between stages. Both are visible in the Spark UI within minutes of investigation.
