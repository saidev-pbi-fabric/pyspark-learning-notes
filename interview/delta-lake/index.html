    Delta Lake¶

    16. Delta Table Writes¶

    Q: How do you write PySpark data to Delta tables?

    30-sec answer

    Use the DataFrame write API with format("delta"). You specify the write mode — append to add rows, overwrite to replace the table — and either a path or a table name registered in the metastore. Delta wraps the write in a transaction, so it's atomic and logged.

    Deep dive

    # Write to path
df.write.format("delta").mode("append").save("/mnt/silver/transactions")

# Write to table (registers in metastore)
df.write.format("delta").mode("overwrite").saveAsTable("silver.transactions")

# With partitioning
df.write.format("delta") \
    .mode("overwrite") \
    .partitionBy("event_date") \
    .save("/mnt/silver/events")

# Overwrite specific partitions only (dynamic partition overwrite)
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")
df.write.format("delta").mode("overwrite").save("/mnt/silver/events")

    Write modes:

    Mode Behaviour
    append Adds new files, never deletes existing data
    overwrite Replaces the entire table contents
    ignore Does nothing if table/path already exists
    error Raises error if table/path already exists (default)

    What happens under the hood: 1. Spark writes new Parquet files to the Delta table directory 2. Delta logs the operation in the _delta_log/ transaction log (a JSON commit file) 3. The write is atomic — readers see either the full new data or the old data, never a partial state

    Schema enforcement: Delta rejects writes where the incoming schema doesn't match the table schema. This catches pipeline bugs early instead of silently corrupting data.

    # Enable schema evolution — add new columns from source automatically
df.write.format("delta") \
    .option("mergeSchema", "true") \
    .mode("append") \
    .save("/mnt/silver/transactions")

    Follow-up: Why use Delta tables?

    30-sec answer

    Delta gives you three things standard Parquet doesn't: ACID transactions (writes are atomic, no partial reads), schema enforcement (bad data rejected at write time), and time travel (query any previous version with VERSION AS OF). For production pipelines these aren't nice-to-haves — they're what makes pipelines reliable.

    17. MERGE Upserts¶

    Q: How do you implement upserts in Delta?

    30-sec answer

    Use the Delta MERGE operation — it compares source and target data on a match condition, updates matching rows, inserts new ones, and optionally deletes rows that no longer exist in the source. It's the standard pattern for incremental pipeline loads.

    Deep dive

    from delta.tables import DeltaTable

target = DeltaTable.forPath(spark, "/mnt/silver/customers")
source = spark.read.format("delta").load("/mnt/bronze/customers_new")

target.alias("target").merge(
    source.alias("source"),
    "target.customer_id = source.customer_id"
).whenMatchedUpdate(set={
    "name": "source.name",
    "email": "source.email",
    "updated_at": "source.updated_at"
}).whenNotMatchedInsert(values={
    "customer_id": "source.customer_id",
    "name": "source.name",
    "email": "source.email",
    "updated_at": "source.updated_at"
}).execute()

    Full SCD Type 1 + delete pattern:

    target.alias("target").merge(
    source.alias("source"),
    "target.customer_id = source.customer_id"
).whenMatchedUpdate(set={...})   # Update existing
.whenNotMatchedInsert(values={...})  # Insert new
.whenNotMatchedBySourceDelete()  # Delete removed records
.execute()

    Performance considerations: - MERGE is expensive — it scans both source and target to find matches - Always filter source to only changed/new records before the MERGE - Partition the target table on a date or batch column so MERGE only touches relevant partitions - Use whenMatchedUpdateAll() and whenNotMatchedInsertAll() for brevity when column names align

    CDC pattern (Change Data Capture): 

    # Source has a 'operation' column: I=insert, U=update, D=delete
target.alias("t").merge(
    source.alias("s"),
    "t.id = s.id"
).whenMatchedDelete(condition="s.operation = 'D'") \
 .whenMatchedUpdateAll(condition="s.operation = 'U'") \
 .whenNotMatchedInsertAll(condition="s.operation = 'I'") \
 .execute()

    Follow-up: Why is MERGE important?

    30-sec answer

    MERGE is what enables incremental pipelines — you only process new or changed data instead of reloading full tables on every run. It replaces the manual pattern of read-full-table, apply-changes, overwrite — which is both slow and risky. With MERGE, incremental loads are atomic and idempotent.

    18. Delta Table Maintenance¶

    Q: How do you maintain Delta tables?

    30-sec answer

    Two commands: OPTIMIZE for compacting small files into larger ones (targeting ~1GB), and VACUUM to physically delete data files no longer referenced by the transaction log. Without these, tables accumulate small files over time, which degrades query performance.

    Deep dive

    OPTIMIZE — file compaction:

    -- Compact all files
OPTIMIZE silver.transactions

-- Compact + Z-order on frequently filtered columns
OPTIMIZE silver.transactions ZORDER BY (customer_id, event_date)

    # Via PySpark
from delta.tables import DeltaTable
dt = DeltaTable.forName(spark, "silver.transactions")
dt.optimize().executeCompaction()

    When to run: after bulk appends, nightly after streaming pipelines, after MERGE operations that generate many small files.

    VACUUM — removing obsolete files:

    -- Remove files older than 7 days (default retention)
VACUUM silver.transactions

-- Shorter retention — be careful, disables time travel to that point
VACUUM silver.transactions RETAIN 168 HOURS

    VACUUM and time travel

    VACUUM permanently deletes old data files. After VACUUM, you cannot time travel to versions older than the retention period. Default is 7 days — don't reduce below your SLA for point-in-time recovery.

    The small file problem in detail:

    Every append write creates new Parquet files. A streaming pipeline appending every minute creates 1,440 files per day. After a month: 43,200 files. Spark has to open and read the footer of every single file during a scan — even if most files are filtered away by partition pruning. OPTIMIZE merges those into a handful of 1GB files.

    Databricks managed OPTIMIZE: On Databricks, Auto Optimize and Auto Compaction can be enabled on tables: 

    ALTER TABLE silver.transactions SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',
  'delta.autoOptimize.autoCompact' = 'true'
)

    Follow-up: Why is maintenance necessary?

    30-sec answer

    Without regular OPTIMIZE, append-heavy tables accumulate thousands of small files. Each file has overhead — Spark opens it, reads the footer, checks statistics. At scale, that metadata cost makes even simple queries slow. VACUUM clears dead files that are no longer in the transaction log, reclaiming storage and keeping the file listing lean.

    19 & 20. File Size, Layout Optimisation & Data Skipping¶

    These three concepts are tightly linked — covered together.

    Q: What file size works best for Delta tables?

    30-sec answer

    Target 100MB to 1GB per file. Below 100MB and you start seeing metadata overhead dominate query time. Above 1GB and you reduce parallelism — fewer files means fewer tasks means fewer executors doing useful work in parallel.

    Q: How do you optimise Delta table layout?

    30-sec answer

    Use Z-ordering to co-locate related data within files based on frequently filtered columns. On Microsoft Fabric, V-Order adds additional Parquet-level compression. Both techniques improve data skipping — Delta reads fewer files because related data is physically grouped together.

    Q: What is data skipping?

    30-sec answer

    Delta stores min/max statistics for each column in each file. When a query has a filter, Delta checks those statistics and skips any files that can't contain matching rows — without opening them. Z-ordering makes data skipping more effective by ensuring similar values are in the same files.

    Deep dive

    File size and parallelism:

    Spark assigns one task per file. If you have 5 executors and 5 files of 1GB each, all executors work simultaneously. If you have 5 executors and 500 files of 10MB each, Spark runs 100 rounds of 5 tasks — most time is spent in task scheduling overhead.

    Ideal target: 

    Total data size ÷ number of cores = target file size
(aim for ~200MB–1GB per file)

    Z-ordering:

    Z-order is a space-filling curve that interleaves multiple column values into a single ordering. This means rows with similar values in multiple columns end up in the same files — making multi-column filter queries extremely efficient.

    OPTIMIZE silver.events ZORDER BY (customer_id, event_date)

    Without Z-order: a filter on customer_id = 'X' AND event_date = '2025-01-15' might need to scan 500 files With Z-order: the same filter might touch only 3–4 files

    V-Order (Microsoft Fabric specific):

    V-Order is Fabric's proprietary Parquet optimisation — it applies additional sorting, dictionary encoding, and compression within each Parquet file. It's enabled by default in Fabric and makes reads faster without any code changes.

    Data skipping in practice:

    # Delta automatically collects stats on write
# Check stats with:
dt = DeltaTable.forName(spark, "silver.events")
dt.detail().show()

# See how many files are being scanned vs skipped
spark.conf.set("spark.databricks.delta.stats.skipping", "true")

    When data skipping is most effective: - After Z-ordering on query predicates - On tables with good file size (not too small, not too large) - When filters are on columns with reasonable cardinality (not boolean columns)

    Follow-up: Why is layout optimisation important?

    30-sec answer

    It's what makes Delta tables fast at query time. Without Z-ordering, data is laid out in the order it arrived — filters scan every file looking for matches. With Z-ordering on your most filtered columns, the same query touches a fraction of the files. On a 10TB table, that's the difference between a 2-minute scan and a 5-second one.
