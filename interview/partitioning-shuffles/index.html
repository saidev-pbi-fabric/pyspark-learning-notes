    Partitioning & Shuffles¶

    10. Partition Strategy¶

    Q: How should tables be partitioned in lakehouse environments?

    30-sec answer

    Partition only on columns that are consistently used in filters — typically date fields like event_date or load_date. Avoid high-cardinality columns. In Delta tables specifically, over-partitioning creates a metadata problem that slows down reads more than it helps them.

    Deep dive

    Partitioning in Delta/Parquet means physically splitting data into separate folders based on column values:

    /silver/events/event_date=2025-01-01/part-00001.parquet
/silver/events/event_date=2025-01-02/part-00001.parquet
...

    When a query filters on event_date, Spark skips all non-matching folders entirely — this is partition pruning, and it's fast.

    What goes wrong with bad partitioning:

    Problem Cause Effect
    Too many partitions Partitioning on high-cardinality column (e.g., user_id) Millions of tiny files, slow metadata operations
    Too few partitions Only one or two distinct values (e.g., is_active) No benefit, large files per partition
    Wrong column Partitioning on a column rarely filtered No pruning benefit, just fragmentation

    The small file problem: Each file has overhead — a Delta transaction log entry, file open/close cost, metadata in the Parquet footer. When you have millions of 1KB files, that metadata overhead dominates. A table with 10,000 x 1MB files is slower to query than one with 100 x 100MB files containing the same data.

    Delta-specific guidance: - Date columns (day-level) work well for most event tables - Avoid partitioning on columns with more than ~10,000 distinct values - Use Z-ordering within partitions for further data skipping - Run OPTIMIZE after bulk loads to compact small files

    Follow-up: What happens with excessive partitioning?

    30-sec answer

    Excessive partitioning creates two problems: metadata overhead and small files. Delta's transaction log has to track every file in every partition — with millions of partitions, even listing files becomes slow. And many small files mean Spark spawns thousands of tiny tasks, where task setup cost exceeds actual compute time.

    11. Repartition vs Coalesce¶

    Q: What is the difference between repartition() and coalesce()?

    30-sec answer

    repartition(n) does a full shuffle to redistribute data evenly across n partitions — it can increase or decrease partition count. coalesce(n) only reduces partitions by merging them locally without a shuffle, making it cheaper but potentially leaving uneven partition sizes.

    Deep dive

    # Full shuffle — data redistributed evenly across 200 partitions
df_repart = df.repartition(200)

# No shuffle — merges existing partitions locally, reduces to 10
df_coalesce = df.coalesce(10)

# Repartition by column — ensures all rows with same key go to same partition
df_by_key = df.repartition(200, col("customer_id"))

    When to use each:

    Scenario Use
    Writing output files — want fewer, evenly-sized files coalesce()
    Before a join on a key column — align partitioning repartition(n, col)
    After a filter that dramatically reduced data size coalesce()
    Need guaranteed even distribution repartition()
    Need to increase partition count repartition() only — coalesce can't increase

    The hidden cost of repartition(): It triggers a full shuffle — all data moves across the network. Use it deliberately. If you're just reducing partitions before a write, coalesce() is almost always the right choice.

    Practical write pattern: 

    # After heavy transformations, reduce to sensible file count before writing
df_final.coalesce(10).write.format("delta").mode("overwrite").save("/gold/output")

    Follow-up: When should coalesce() be used?

    30-sec answer

    Use coalesce() when reducing partitions before writing output files — it avoids an unnecessary shuffle. After filtering a large dataset down to a fraction of its original size, coalesce brings the partition count down without the cost of moving data across the network.

    13. Shuffle Operations¶

    Q: Why are shuffle operations expensive?

    30-sec answer

    A shuffle moves data between executors across the network so records with the same key end up on the same partition. This involves serialising data, writing shuffle files to disk, transferring them over the network, and reading them back. Each of those steps is orders of magnitude slower than in-memory computation.

    Deep dive

    What happens during a shuffle:

    Stage 1 (map side):
  Each executor processes its partition
  → Sorts output records by target partition key
  → Writes shuffle files to local disk

Network transfer:
  Executors fetch the shuffle files they need from other executors

Stage 2 (reduce side):
  Each executor reads its portion of shuffle data
  → Deserialises and processes

    Why disk I/O hits hard: Spark writes shuffle data to local executor disk before sending it. If executors run out of disk space, jobs fail. If disks are slow (spinning HDDs), shuffles become a bottleneck even before the network.

    Operations that cause shuffles:

    Operation Why it shuffles
    groupBy() + agg() All rows with same key must meet on one executor
    join() (sort-merge) Both sides sorted and co-partitioned by join key
    distinct() All copies of same value must be on one executor
    repartition() Explicit redistribution
    orderBy() Global sort requires all data on one executor then re-distributed

    How to reduce shuffle cost: 1. Use broadcast joins when one side is small (eliminates shuffle on large side) 2. Filter and project before joins (less data to shuffle) 3. Pre-partition on join keys if joining repeatedly on the same key 4. Tune spark.sql.shuffle.partitions (default 200 — often wrong for your data size)

    Follow-up: How do you minimise shuffles?

    30-sec answer

    Use broadcast joins for small tables — this eliminates the shuffle on the large side entirely. Pre-filter and project before any join to reduce the data volume being shuffled. Tune spark.sql.shuffle.partitions to match your actual data size — 200 is often too high for small datasets and too low for large ones.

    15. Data Skew¶

    Q: What is data skew?

    30-sec answer

    Data skew happens when data is unevenly distributed across partitions — typically because one key value appears far more often than others. One executor ends up processing 80% of the data while others sit idle, making the whole job wait for that one slow task to finish.

    Deep dive

    Classic skew scenario: you're joining a transactions table to a customers table on customer_id. One customer has 50 million transactions (a corporate account), while most have a few hundred. The partition holding that customer's key runs 100x longer than all others.

    How to identify skew: - Spark UI: look for one task in a stage taking 10x longer than others - Stage timeline: all tasks finish quickly except one or two outliers - df.groupBy("key").count().orderBy(col("count").desc()).show() — spot dominant keys

    Fix 1: Salting Add a random suffix to the skewed key to spread it across multiple partitions:

    from pyspark.sql.functions import concat, col, lit, floor, rand

# Add salt to the large table
salt_factor = 10
df_large = df_large.withColumn("salted_key",
    concat(col("customer_id"), lit("_"), (floor(rand() * salt_factor)).cast("string")))

# Explode the small table to match all salt values
from pyspark.sql.functions import explode, array
df_small = df_small.withColumn("salt_range", array([lit(i) for i in range(salt_factor)]))
df_small = df_small.withColumn("salt", explode(col("salt_range")))
df_small = df_small.withColumn("salted_key",
    concat(col("customer_id"), lit("_"), col("salt").cast("string")))

# Now join on salted key
result = df_large.join(df_small, "salted_key").drop("salted_key", "salt", "salt_range")

    Fix 2: AQE skew handling In Spark 3.x with AQE enabled, skewed partitions are automatically detected and split:

    spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")

    Fix 3: Repartition before join 

    df_large = df_large.repartition(200, col("customer_id"))

    Follow-up: How do you fix data skew?

    30-sec answer

    Two main approaches: salting and AQE. Salting adds a random suffix to skewed keys, distributing one hot partition across many — you then explode the smaller side to match. AQE (enabled by default in Spark 3.2+) detects skewed partitions at runtime and splits them automatically. For known skew patterns, repartitioning on the join key before the join also helps.
