    Spark Core Concepts¶

    1. Role of PySpark in Lakehouse Platforms¶

    Q: Where does PySpark fit in modern lakehouse architectures?

    30-sec answer

    PySpark is the distributed processing engine at the core of lakehouse platforms like Databricks and Microsoft Fabric. It handles large-scale transformations on data stored in Delta tables — powering ETL pipelines, feature engineering, streaming, and analytical workloads. It sits between raw storage and the consumption layer.

    Deep dive

    A lakehouse combines the flexibility of a data lake with the reliability of a data warehouse. PySpark is what makes the "processing" layer of that architecture work at scale.

    In practice, the flow looks like this:

    Raw files (Parquet / CSV / JSON in OneLake or S3)
        ↓
    PySpark transforms (clean, join, aggregate)
        ↓
    Delta tables (Bronze → Silver → Gold)
        ↓
    BI / ML / Analytics consumers

    PySpark abstracts the complexity of distributed computing — you write Python DataFrame code, and Spark distributes execution across a cluster automatically. On Databricks, this is backed by the Photon engine. On Fabric, it runs on managed Spark pools against OneLake.

    Why not just use SQL for everything? SQL is great for querying, but complex transformations — schema evolution, conditional logic, looping over datasets, ML feature pipelines — need a programmatic engine. PySpark gives you that without leaving the distributed execution model.

    Follow-up: Why is PySpark preferred for large-scale ETL?

    30-sec answer

    Spark splits data into partitions and processes them in parallel across executor nodes. A transformation that would take hours on a single machine runs in minutes when distributed. It also optimises execution automatically through the Catalyst query planner — so you don't need to hand-tune every query.

    2. DataFrame API vs RDD¶

    Q: Why is the DataFrame API preferred over RDD?

    30-sec answer

    DataFrames sit on top of Spark's Catalyst optimizer and Tungsten execution engine. This means Spark can automatically reorder operations, push filters down to storage, and generate efficient bytecode at runtime. RDDs have none of that — every operation runs exactly as written, with no automatic optimisation.

    Deep dive

    RDDs (Resilient Distributed Datasets) were the original Spark abstraction. They're powerful but low-level — you manage partitioning, serialisation, and execution logic yourself.

    DataFrames add a structured schema layer on top, which unlocks:

    Feature RDD DataFrame
    Catalyst optimisation No Yes
    Tungsten memory management No Yes
    Predicate pushdown No Yes
    Python → JVM overhead High Low (Tungsten bypasses JVM for columnar ops)
    Readable code Verbose Concise

    In production, DataFrames are almost always the right choice. The Catalyst optimizer builds a logical plan from your code, optimises it (reordering filters, pruning columns, choosing join strategies), and compiles it to an efficient physical plan before execution.

    When RDD still makes sense: - You need fine-grained control over partitioning logic - Working with unstructured data that has no schema - Custom serialisation requirements - Iterative ML algorithms that need direct partition manipulation

    Follow-up: When would you use RDD instead?

    30-sec answer

    Only when you need low-level control that the DataFrame API can't provide — such as custom partition logic, unstructured data without a fixed schema, or operations that require direct access to individual records without schema inference.

    3. Lazy Evaluation¶

    Q: What is lazy evaluation in Spark?

    30-sec answer

    Spark does not execute transformations when you write them. Instead, it records each operation in a logical plan and waits. When an action is triggered — like count() or write() — Spark compiles the full plan, optimises it, and only then runs computation across the cluster.

    Deep dive

    Lazy evaluation is one of the most important design decisions in Spark. It lets Spark see the full picture of what you want to do before deciding how to do it.

    Example — without lazy evaluation, this would scan the full table three times:

    df = spark.read.format("delta").load("/data/orders")
df_filtered = df.filter(col("country") == "UK")
df_renamed = df_filtered.withColumnRenamed("order_id", "id")
df_final = df_renamed.select("id", "amount")

    With lazy evaluation, Spark sees all four steps together. Before execution it: 1. Pushes the filter down to storage (only reads UK rows) 2. Prunes columns (only reads order_id and amount) 3. Combines all steps into a single scan pass

    The result: one efficient scan instead of four.

    The DAG connection

    Each transformation adds a node to the DAG (Directed Acyclic Graph). When an action fires, Spark submits the full DAG to the scheduler, which breaks it into stages and tasks.

    Follow-up: What triggers execution?

    30-sec answer

    Actions trigger execution. Common ones: count(), collect(), show(), write(), first(), take(n), save(). Transformations like filter(), select(), join() never trigger execution on their own — they only build the plan.

    4. Transformations vs Actions¶

    Q: What is the difference between transformations and actions?

    30-sec answer

    Transformations build the execution plan — they're lazy and return a new DataFrame without running anything. Actions trigger actual computation and either return a result to the driver or write data to storage. This split is what enables Spark's query optimisation.

    Deep dive

    Type Behaviour Examples
    Narrow transformation No shuffle, each partition maps to one output partition filter(), select(), withColumn(), map()
    Wide transformation Requires shuffle across partitions groupBy(), join(), distinct(), orderBy()
    Action Triggers execution, returns result count(), collect(), show(), write(), first()

    Why the distinction matters in production:

    Wide transformations (shuffle operations) are the expensive ones — data has to move across the network between executors. Every groupBy() or join() on unpartitioned data causes a full shuffle. Knowing this helps you design pipelines that minimise data movement.

    # This builds a plan — nothing runs yet
df = spark.read.format("delta").load("/silver/transactions")
df_agg = df.filter(col("status") == "completed").groupBy("customer_id").agg(sum("amount"))

# This triggers execution — everything above runs now
df_agg.write.format("delta").mode("overwrite").save("/gold/customer_spend")

    Follow-up: Example?

    30-sec answer

    select(), filter(), withColumn(), join() are all transformations — they return DataFrames and add nodes to the plan. count(), collect(), show(), and write() are actions — they submit the plan for execution and return a result.

    5. Spark DAG Execution Model¶

    Q: How does Spark execute jobs internally?

    30-sec answer

    When an action is triggered, Spark converts the transformation chain into a DAG — a directed acyclic graph of operations. The DAG Scheduler breaks this into stages at shuffle boundaries. Each stage is divided into tasks, one per partition, and those tasks run in parallel across executor nodes.

    Deep dive

    The execution flow from code to result:

    Your PySpark code
      ↓
  Logical Plan (Catalyst parses and validates)
      ↓
  Optimised Logical Plan (Catalyst applies rules: pushdown, pruning)
      ↓
  Physical Plan (Catalyst selects join strategy, scan method)
      ↓
  DAG of RDD operations
      ↓
  DAG Scheduler → splits into Stages at shuffle boundaries
      ↓
  Task Scheduler → assigns Tasks (one per partition) to Executors
      ↓
  Executors run tasks in parallel

    Stages and tasks: - A stage is a group of tasks that can run without a shuffle - A task processes one partition - Stage boundaries are always shuffle operations (groupBy, join, repartition)

    Why this matters: If you see a query that has many stages in the Spark UI, each stage boundary is a shuffle. Each shuffle writes data to disk and reads it back — that's where most job time is spent. Reducing stage count = reducing shuffles = faster jobs.

    Follow-up: What determines stage boundaries?

    30-sec answer

    Shuffle operations determine stage boundaries. Any operation that requires data to move between partitions — groupBy(), join(), distinct(), repartition() — creates a new stage. Within a stage, all tasks run independently without any data exchange.
